## What a player sees

**First arrival.** An issued campaign URL opens the real, interactive camp. During session resolution the game shows its existing loading behavior. Once the live session resolves as signed out and the camp is in view, show a compact, nonmodal welcome card with the gold play button. Use the camp’s dark surfaces, serif heading and gold action. At 360 px, use 12 px side margins and a lower safe-area slot above the touch menu and HUD, with stacked actions of at least 44 px each. Keep the arena visible above the card. On a 1280×720 desktop, place the card near the lower left, clear of the rail and its controls. The card has no backdrop, initial focus grab or focus trap. Let it grow for larger text and move it into a scrollable safe area if the viewport is short. Camp pan, zoom, public menus and Game Info remain available around it.

**One join action.** While the card is visible, it takes the place of the existing corner Google button and leaves Game Info available. Defer a colliding noncritical camp callout and give active game sheets, notices requiring an action, and deep-linked replay or expedition scenes their usual priority. An intentional open of a public menu or scene closes the welcome for this tab, so its own controls and any contextual sign-in remain usable. The card remains a labeled region in the normal tab order. Visible keyboard focus and screen-reader access apply to both buttons.

**Dismissal.** “Explore the camp” closes the card immediately, restores the corner join button and leaves the visitor in the same camp view. Escape does the same while focus is in the card. Preserve focus on the newly opened surface when that caused the dismissal. For button or keyboard dismissal, move focus to the restored join button, with the camp landmark as a fallback. Remember dismissal across reloads and campaign links in the same tab using a separate session flag. If session storage fails, remember it for the current document while it lives. Panning or an incidental tap outside the card leaves it in place. The visitor can still watch the camp and replays and can join later from the corner or a contextual action.

**Sign-in.** “Play free in your browser” starts the existing Google flow with one activation. Reuse its busy and startup-error states. While Google opens, keep focus, guard repeat activation and temporarily disable the secondary action so it cannot report a dismissal immediately before navigation. On startup failure the card enables both actions again and announces the existing retry text. Browser Back from Google restores the campaign entry and allows retry if the welcome was still open. A canceled or failed OAuth callback lands on the regular `/game/` visitor camp with its existing notice and join control. On success the app goes to `/game/`, opening the existing creation dialog only if this account needs a gladiator. OAuth provider, scopes, PKCE, redirect allow-list and callback cleanup stay as they are. Google sign-in and gladiator creation are distinct steps.

**Returning and direct visits.** A signed-in player on a campaign URL gets normal play immediately, including when owner data is loading, unavailable, or empty. Signing in via another tab removes any open welcome. Do not show the welcome during unresolved or unavailable Auth, after a deliberate sign-out on the same loaded page, in fixture mode, or on `/` and `/game/` direct or shared links. Require a confirmed signed-out result for the promo. The existing session hook can display the visitor shell on a failed auth lookup, so preserve that shell behavior and keep the welcome hidden on failure. The camp and sign-in have no dependency on campaign storage or visit reporting. [Session hook](../../../src/lib/api/session.ts)

## Campaign links and browser attribution

**Recommend real static paths** on the production origin, for example `https://cloudiator-arena.pages.dev/game/p/yt-profile/`. Render the same camp and leave the campaign path visible. Define one stable code for each channel placement or individually linkable video or ad, e.g. `yt-profile`, `yt-trailer`, `ig-bio`, `reddit-webgames-01`, `itch-page`, `reddit-ad-01`. The registry maps each code to a channel and a specific placement or creative for weekly rollups. Never reuse a retired code for a different source. The promotion plan’s `?ref=` profile examples would use the corresponding static paths once approved. Exact paths are reportable dimensions where supported and work when a platform drops query parameters. `?ref=` would make minting links simpler and would reuse `/game/` as-is. All those links would share a path, and a dashboard’s reliable reporting by arbitrary query is unproven. Adding a path takes a new static export, so include codes for the first launch batch together. Where several Shorts send viewers through a single trailer link, report the shared trailer placement. A distinct video count requires a distinct outbound link that its viewers can actually use.

**Capture on entry.** Pass the exact, registered slug into the shared camp entry. Qualify the welcome and reporting from the current path. Record the first valid source for an anonymous visitor as soon as signed-out status is known, before a join action can leave for Google. Keep the existing Google redirect to `/auth/callback/` and its return to `/game/`. Same-origin `sessionStorage` survives that same-tab round trip, including cancel/fail, Back and normal reload. Use a separate same-origin `localStorage` record for Pioneer’s 30-day handoff and a separate tab flag for welcome dismissal. Auth’s own storage is independent. A different browser or origin, or clearing storage, can lose the record. Losing access to either attribution store still allows the other to work. Landing counts come from the actual incoming path, independently of stored attribution.

**Contract for 2.0.** Tab key `cloudiator.promo.source.v1` holds `{"v":1,"code":"yt-trailer","capturedAtMs":1795680000000}`. Pioneer’s same-origin local key `cloudiator.signup-source.v1` holds `{"code":"yt-trailer","capturedAtMs":1795680000000}`. Both expire 30 days after the original capture. Keep the earliest valid stored capture without refreshing its timestamp. Slugs use 1–24 lowercase ASCII letters, digits and single separating hyphens with no leading or trailing hyphen. Check the exact registered browser pathname before showing the welcome or writing storage. Reject malformed, unregistered, expired or future-dated records when reading. Share the registry with 2.0. Account association, consumption and durable sign-up storage belong to 2.0. A player who arrives already signed in contributes a path request where measurable. Their visit creates no attribution record.

**Abuse and privacy.** The code is a public, editable reporting label. Never use it for identity, access, redirects, referral credit, rewards, entitlements, pricing or any gameplay outcome. Leave unknown paths to the existing static 404. Bare camp links and unrelated queries, including `?ref=`, cannot create an attribution record or open the card. Reject malformed or oversized values, encoded separators and unexpected segment shapes. Never echo the submitted string into copy, HTML, logs added by the client, or provider URLs. Do not append it to OAuth state, redirect URLs, tokens, requests to Supabase or player records. The landing path is visible to the host by design. Browser attribution stores only the code, the capture timestamp and the tab schema version. Do not join that record with a browser identifier, account ID, email, raw referrer or IP in 1.9.4. A copied link credits its label to that request, regardless of who shared it. A scripted client can request a valid path repeatedly. Both facts limit what the totals mean.

## Visit measurement before 2.0

| Option | What it could count | Limits and dependencies |
| --- | --- | --- |
| **Recommended · Cloudflare host request analytics by path, subject to proof** | Weekly successful landing-document requests for each issued path, with no new browser request, script or CSP entry. | Requires exact path and production-host visibility on this Pages project. Repo evidence confirms the `pages.dev` host and static export, but does not establish access to per-path request analytics. Cloudflare HTTP analytics can be zone-scoped, and Pages Web Analytics is a separate browser product. A counter can include bots, previews, reloads and repeat visits. Browser cache, sampling and reporting limits can hide loads. It cannot identify human visitors, sign-in outcomes, new gladiators or retention. |
| Cloudflare Web Analytics · outside 1.9.4 | Cookieless browser pageviews by landing path if the project and report support it. A JavaScript pageview can omit some previews that never execute the beacon. | Requires a Cloudflare setting and a CSP change for the Cloudflare Insights script and its configured collector. The browser beacon is outside the approved no-tracker release. Blockers, disabled JS, sampling or reporting behavior can miss events. It does not link an arrival to Google completion or a new gladiator. |
| No collector · browser storage and channel reports | A browser can retain its own first source. Some channels expose outbound clicks for a link or ad. | Browser storage cannot aggregate across browsers. Platform clicks measure clicks where available and can differ from successfully loaded camp visits. An extra static pixel would still need measurable host path analytics. A new same-origin collector using a Worker, Pages Function, Edge function, API or database is outside 1.9.4. |

**Before the client release.** On the actual production project, check read-only whether Avi can report weekly successful landing HTML requests by exact path and host on `cloudiator-arena.pages.dev` without a beacon. Capability is unverified in this offline design. If passive path reporting is unavailable, Avi approved proceeding with the front door. Report channel outbound clicks where supported and leave Phase 0 visit counting open. Any Cloudflare settings change needs its own go.

**After the authorized deployment.** When passive path counts are available, verify filters and aggregation with controlled loads of two registered paths, a direct camp load and an unregistered path. Each registered landing should appear on its own row. Its assets and callback, and the direct and unknown loads, should stay out of campaign totals. Confirm trailing-slash behavior, reporting lag, inclusion of browser reloads and known previews, and whether numbers are sampled. Exclude preview hosts and redirects. Use the numbers for promotion decisions only after this check passes.

**Weekly report.** Record the reporting window and timezone (recommend UTC), per-code counts with the metric and filters named, and channel rollups. Use “landing requests” for the host count. Keep the promotion plan’s independent weekly total of newly created human gladiators from the authorized read-only report. Before 2.0, these numbers cannot establish by-source sign-ups, sign-up conversion, cost per sign-up, seven-day activity, or sign-in abandonment. ## Static export and CSP

- Preserve `output: 'export'`, `trailingSlash: true`, the existing Suspense boundary for query-driven behavior, and the `out/` deployment. Generate each issued path at build time from the registry, for example with `generateStaticParams` and no dynamic fallback. Each must directly return its own exported camp document with status 200. Preserve regular `/game/`, root and scene behavior. Avoid client redirects, internal prefetches or automatic fetches of promo pages that could inflate counts. Never route arbitrary paths to the welcome. Use the project-local installed Next guide named in `AGENTS.md` when implementing. - Keep the generated Pages `_headers` policy intact. `script-src` permits the site and inline scripts and `connect-src` permits the site and the exact configured Supabase origin. Preserve the referrer policy, asset rules, and fixed auth callback. Verify the effective headers and CSP on the served campaign pages. - Keep the trailer as a promotion asset. The camp adds no video embed, ad SDK, new tracker, server route, database migration, Edge deployment or change to Google/Supabase Auth configuration. Keep the locked dependency install and build/browser output separation in `AGENTS.md`. Production deployment and any settings action follow the project’s release approval.
